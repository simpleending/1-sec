## Implemented: keep authenticated requests within their origin

Recent advisory updates describing redirect credential leakage prompted inspection of 1SEC's own Go HTTP clients. The MCP TypeScript SDK and `follow-redirects` advisories are research inputs, not installed vulnerable dependencies. Publication dates differ between the global advisory feed and some maintainer pages; this cycle selected qualifying **updated** records and does not describe them all as newly published this week.

The actual source paths used Go's default redirect policy. JSON bodies constructed with replay support could be resent on HTTP 307/308. Standard bearer filtering is based on domain relationships rather than the complete origin; custom API-key headers do not receive the same protection. An upstream redirect could therefore disclose OAuth request secrets, optional AI API keys, cloud data or CLI request bodies.

The shared authenticated client now checks the original scheme, hostname and effective port before every redirect, including subsequent hops. It rejects other origins and URL user information, permits ordinary same-origin moves, and retains the ten-request redirect ceiling. Hostname comparison folds ASCII letters only: Unicode case folding can equate different IDNA destinations. Non-ASCII spellings must match exactly; equivalent alternate Unicode/punycode spellings may require configuring the canonical endpoint explicitly.

The client is used by Token Vault, the optional Gemini integration, GitHub Actions collection, cloud ingestion and command polling/ACK, all six CLI API helpers, and archive restore. Existing public-only webhook DNS/address checks remain separate. A blocked redirect returns a real error, not a successful response containing a 3xx status. Cloud ingestion/ACK, archive restore and ordinary CLI helpers also reject non-2xx responses without a usable redirect. Successful empty 204 delivery remains supported.

**Threat precondition:** an attacker must influence a configured upstream response/redirect or an insecure configured HTTP route. This review found no way for an ordinary event submitter to replace Auth0, Google or GitHub destinations. There is no claim of observed credential theft. These controls do not protect secrets after compromise of their legitimate origin, remove initial plaintext HTTP exposure, or sandbox an integration.

## Implemented: validate token exchange results

Token Vault now has a 15-second HTTP deadline in addition to its existing lifecycle context and rejects responses larger than 64 KiB before parsing. Success requires HTTP 200, nonblank visible-ASCII access-token and token-type fields, no whitespace in the token type, and nonnegative expiry. Missing or zero `expires_in` remains allowed because OAuth recommends rather than requires it. Valid opaque access tokens are preserved without trimming or rewriting.

Previously, `{}`, `null` or an HTTP error containing a token-shaped object could increment the success counter. Such responses now record failure. Structured OAuth errors continue through the existing API/alert contract, and both supported subject-token types retain the documented Auth0 JSON request format. These checks establish a well-formed provider result, not cryptographic verification of an opaque external access token.

## Implemented: reject oversized response prefixes

GitHub Actions responses now have a 4 MiB boundary before JSON parsing. HTTP errors no longer read and reflect arbitrary upstream bodies into collector logs. Same-origin API redirects, such as a renamed repository, remain supported. This collector still polls the latest 20 runs and does not promise lossless workflow history.

Cloud command pages retain their 2 MiB per-page limit, but now read at most limit-plus-one and reject oversize before parsing the whole JSON document. A valid command prefix followed by excess padding or another JSON value is no longer accepted. The existing pagination and overall fetch deadline remain. These bounds protect the client, not an unlimited-volume or exactly-once delivery guarantee.

## Verified regressions and delivery

Local race tests for the affected core, Token Vault, GitHub collector, optional AI and CLI packages pass. The redirect tests reproduced cross-origin requests before the fix, including a separate Unicode-host reproduction that reached a distinct IDNA origin before its correction. After correction, the destination is not contacted. Positive controls preserve same-origin POST replay, GitHub rename redirects, ordinary token exchanges, OAuth errors and empty 204 delivery. Negative cases include 301/302/303/307/308, port changes, downgrade, subdomains, user information, redirect caps, malformed token fields/expiry, HTTP failures and padded/trailing JSON.

Full cycle verification records the Go race suite/build/vet/static analysis, package/symbol vulnerability reachability, OSV, Cargo audit/fmt/Clippy/tests and website checks against the final source snapshots. Native collection found no Go/Rust or production website dependency advisories. The existing minimatch development-tool advisory remains a concrete deferral: eight moderate derived audit paths in this run (the earlier snapshot reported 16), one conditional advisory, no production finding. Installed v3 lacks the affected amplification phase and the installed v9 caller uses the default optimization level 1; the reported vulnerable phase requires level 2. A blanket v11 override changes legacy exports. No advisory ignore or forced downgrade was introduced; compatible parent migration remains work.

Windows Rust tests use the portable feature set because full-feature test linking requires Npcap's `wpcap.lib`. Linux CI must verify all features and the real sidecar path. No Rust behavior or dependency versions changed here. These are source changes and a local validation binary; **downloadable v0.4.29 is unchanged** and does not contain this patch. No release tag was created.

## Improve the weekly engineering contract

The local script's 25 regressions now include refusal to leave native dependency findings unreviewed and explicit product outcome accounting. Each cycle records implemented action IDs with engine source and regression paths, or explains why no product patch applies. Workflow/report/website edits do not count as engine improvements. This prevents a reporting-only pass from silently standing in for the requested product work, without forcing speculative patches. Schema checks still cannot prove the reasoning or tests correct.

`AGENTS.md` and the [existing workflow](../weekly-vulnerability-cycle.md) already tell the repository agent to run this process for weekly requests; a separate skill is unnecessary. The script gathers evidence and verifies receipts. The invoked agent performs analysis and implementation, without Gemini or another model API in the script. No unattended AI worker or recurring schedule was created.

## Research retained without unsupported prevention claims

- The [October 30 Microsoft investigation](https://www.microsoft.com/en-us/security/blog/2026/10/30/inside-malicious-claude-code-branded-cursor-extension-persistent-ssh-backdoor/) describes a malicious editor extension attempting SSH authorization changes, reverse forwarding and startup persistence. 1SEC's runtime paths require supplied file/process evidence; they do not enforce extension installation admission or inspect encrypted SSH contents. Generic blocking of SSH, a monitoring-like task name or every package alias would also block legitimate administration. Complete endpoint provenance and a trusted pre-execution admission integration remain separate work; no new campaign-wide prevention claim is made.
- [DBHub's SQL comment discrepancy](https://github.com/bytebase/dbhub/security/advisories/GHSA-j656-3hf2-fvjc) and [functype's package-specifier installation](https://github.com/jordanburke/functype/security/advisories/GHSA-wcjj-9m6g-2fr2) do not identify installed dependencies or an equivalent execution sink here. Existing observed-action heuristics are not SQL parsers or package-manager admission policies. Customer tool runners must enforce least privilege and validated operations before execution.
- [filelock's hard-link/path race](https://github.com/tox-dev/filelock/security/advisories/GHSA-69hj-f68j-2879) requires writable-path and filesystem ownership analysis. The package is absent; private engine directories are the current other-account boundary. Same-account compromise and operator-selected shared directories remain outside that assurance. Adding a symlink check alone would not solve hard links or path replacement.
- KEV's WordPress, Ivanti, GitLab and Cisco entries do not match engine dependencies. Customer asset inventory, vendor patching and exposure management remain necessary. A clear product dependency scan is not an assessment of every device in a customer's network.
