# v0.4.31 — named operator roles and permissions

Release date: November 5, 2026 (Asia/Bangkok).

This release adds individual operator credentials and explicit role permissions to the engine HTTP API. The main agent and optional Rust sidecar are packaged for Linux, macOS and Windows on AMD64 and ARM64. Upgrade both installed binaries together. The Rust version changes for release alignment; its runtime authorization remains the privileged internal broker boundary, separate from HTTP operator roles.

## Roles and permissions

Each operator has one built-in role. IDs are case-sensitive, contain 1–128 ASCII letters, digits, `.`, `_`, `@` or `-`, and cannot be `.`, `..` or the reserved `me`. Unknown roles, permissions and unclassified HTTP routes grant no access. IDs and roles are assigned by an administrator, never taken from caller identity headers or action payloads.

| Role | Granted operations |
| --- | --- |
| `viewer` | Read existing diagnostics, alerts, policies, histories and sensor metadata; inspect its own identity and permissions. |
| `analyst` | Viewer access plus alert-status updates and simulated response-policy tests. Cannot delete alerts or change policy. |
| `responder` | Analyst access plus approve/reject, supported rollback and webhook retry. Cannot change dry-run mode, approval thresholds, policy or credentials. |
| `sensor_manager` | Viewer access plus observation-only sensor enrollment/rotation and sensor revocation. Cannot issue or rotate credentials that authorize local containment. |
| `integration` | Viewer access plus trusted event ingestion, management-access checks and Token Vault exchanges. This is a sensitive gateway/service role: actionable telemetry and asserted end-user identity must be trustworthy. Prefer scoped sensor credentials for ordinary producers. |
| `administrator` | All listed operations, alert deletion, policy/live-mode settings, local containment grants, operator management and engine administration. |

The permission strings returned by `/api/v1/operators/me` are `read`, `alerts.triage`, `alerts.delete`, `response.test`, `approvals.decide`, `response.rollback`, `webhooks.retry`, `policies.manage`, `sensors.manage`, `containment.grant`, `operators.manage`, `events.write`, `access.check`, `tokens.exchange` and `engine.manage`. Each role receives only its listed subset; there is no wildcard or arbitrary permission override.

## Enable and migrate

Existing deployments keep their current shared-key behavior until operators are enabled. Shared write keys remain fully privileged in compatibility mode, and read-only keys retain their existing restrictions. Merely installing v0.4.31 does not convert them into individual identities.

1. Back up configuration and private state. Enable `operators.enabled` with `operators.require_named: false`, retain a private bootstrap write key, and restart. The default state directory is `bus.data_dir/operator-identity`; it must be persistent, engine-owned and private, including its parent directories.
2. Use TLS or a loopback connection to enroll at least two administrators, then assign individual identities to people and services. Save issued tokens securely; the server returns each token once and stores only its SHA-256 hash. Never put an operator or sensor token in `server.api_keys` or `server.read_only_keys`.
3. Migrate clients. Bearer authorization and `X-API-Key` are supported, one credential header at a time. The existing CLI accepts individual tokens through `--api-key` or the client command's `ONESEC_API_KEY`; prefer secret injection rather than putting tokens in shared command history. Do not use that operator token as the server's bootstrap environment key.
4. Disable `cloud.remote_commands_enabled`, set `operators.require_named: true`, and restart. Strict mode rejects shared API keys and unauthenticated management reads, even on loopback. It requires an active named administrator at startup. Health/liveness and the data-free embedded UI shell remain accessible; separately authenticated sensor event submission still works.

For example, the bootstrap administrator can enroll a responder using the engine API:

```sh
curl -X POST http://127.0.0.1:1780/api/v1/operators \
  -H "Authorization: Bearer $BOOTSTRAP_KEY" \
  -H "Content-Type: application/json" \
  --data '{"id":"alice@example.com","role":"responder"}'
```

Use HTTPS for non-loopback requests. A forwarded-protocol header alone does not establish TLS. A trusted TLS-terminating proxy may connect over loopback; it must enforce secure external transport and protect that local path.

## Lifecycle API

| Method and path | Behavior |
| --- | --- |
| `GET /api/v1/operators/me` | Current authenticated identity and effective permissions; legacy clients are explicitly labeled shared-key access. |
| `GET /api/v1/operators` | Administrator-only metadata; no tokens or credential hashes. |
| `POST /api/v1/operators` | Administrator creates `{id, role, expires_at?}` and receives a one-time token. |
| `PATCH /api/v1/operators/{id}` | Administrator changes `{role}`; subsequent authorization uses the current role. |
| `POST /api/v1/operators/{id}/rotate` | Administrator receives a fresh token, invalidating the prior credential. Optional `{expires_at}` renews validity; default is 90 days from rotation. Can renew an expired, non-revoked identity. |
| `POST /api/v1/operators/{id}/revoke` | Permanently revokes that identity. It cannot be rotated, reactivated or re-enrolled under the same ID. |

Expiry defaults to 90 days and cannot exceed one year at issuance/rotation. The last active administrator cannot be demoted or revoked; create another administrator first. Monitor expiry and keep an offline recovery plan. If every administrator expires or its credential is lost, an engine owner can stop the service, temporarily disable strict mode in the private configuration, provide a new private bootstrap key, restart and rotate a non-revoked administrator. Re-enable strict mode after recovery. A permanently revoked identity requires a new ID. This recovery requires control of the engine host/configuration; it is not a remote anonymous bypass.

## What is enforced

- Every named request is authenticated and checked against an explicit method/path permission. Request-supplied role/actor fields do not elevate authority. Sensor credentials remain ingestion-only; operator credentials do not become broker credentials.
- Credentials use 32 random secret bytes with separate identity prefixes and credential IDs. Roles, rotation, expiry and revocation survive restart. The private append journal is exclusively owned by one engine and synced before a grant is committed. Corruption, partial records, failed writes and capacity failure stop operator authorization; readiness reports the failed identity subsystem.
- Administrator identity changes recheck the current credential and role under the same lock as the journal commit. A revocation during body parsing cannot leave a newly issued administrator credential. Sensor credential issuance/rotation is fenced against operator revocation, and local-containment permission is checked against the actual stored sensor grant under its rotation lock.
- Approval history records `operator:<id>`. API audit records include identity, credential ID, role, method, path and result without recording credential headers or issued secrets. Approval dispatch rechecks the credential's current permission, including after rotation, revocation or role downgrade and immediately before execution.
- The embedded dashboard displays the identity/role and uses effective permissions for controls. Refresh rechecks capabilities; revoked/expired credentials clear the active credential and snapshot on authorization failure. Server checks remain authoritative.
- Strict mode cannot be paired with legacy cloud command execution. Both startup validation and the command executor reject that path; a cloud-supplied display name is not a named operator credential. Cloud telemetry reporting remains separate.

## Validation and limits

Regression coverage includes the six-role endpoint matrix, every registered API route, unknown/malformed methods and paths, spoofed actor headers/payloads, credential/hash disclosure, TLS/ambiguous headers, restart/rotation/revocation/expiry, journal failures and limits, last-administrator protection, concurrent authorization and credential-grant fencing. Harmless spies cover shutdown/live response routes; no real kill, account change or firewall action is used. Actual approval dispatch tests use a mock executor and prove that revoked/rotated/downgraded approvers cannot execute, while an active responder can. Embedded UI tests cover role-specific controls and authorization failure handling.

The final source is checked with the Go race suite, build/vet/static analysis, package/symbol vulnerability reachability, OSV and the repository-wide Rust/website dependency gates. Windows portable Rust tests retain the documented Npcap linking limitation; Linux CI verifies full-feature Rust and real sidecar integration. Release jobs verify native versions where possible, all 22 release assets, both signed checksum manifests and archive checksums before publication. Cross-built targets are not claimed to have been natively executed. Cargo cache restoration reuses prior build dependencies/tools; audits and version checks still run.

These identities authenticate possession of a named bearer credential, not human presence, SSO, MFA, device attestation or external directory membership. Roles apply to one engine's HTTP API; they do not implement tenant/resource scoping, custom roles, two-person approval, or operator permissions on the separate cloud website or privileged broker. Keep privileged host/configuration/broker credentials private. Already executing actions cannot be recalled; previously issued independent credentials are not automatically revoked when their issuer loses access. Other admitted in-flight requests may finish their operation. Operator state supports at most 1,000 total identities and a journal below 16 MiB, with no compaction or replication yet. Do not restore old journals over current revocations: stale backups can restore old credentials. File permissions and sync are not tamper-resistant, off-host or power-loss recovery guarantees. Request logs and approval histories are not a durable compliance audit trail. Fleet collection durability, measured capacity, PID start-time binding and enterprise/government assurance remain separate work.
