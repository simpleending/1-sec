# October 14, 2026: management access before equipment control

The France refrigeration incident prompted a general access-control improvement. These changes are released after the incident. They do not establish that 1-SEC was deployed at affected stores or would have stopped the actual exploit, whose entry method remains unconfirmed.

## Implemented controls

- `POST /api/v1/access/check` gives a trusted management gateway an explicit allow/deny decision before forwarding a protected request. It requires an existing write-scope API key. Read-only keys and unauthenticated callers cannot obtain authorization decisions.
- A configured source IP/CIDR and an exact configured operator identity must both match. The gateway must independently verify the identity. Empty policy, uninitialized policy, missing context, invalid addresses, unverified identity, or unknown operators deny access. IPv4-mapped IPv6 clients use canonical IPv4 matching; scoped addresses and hostname impersonation are rejected.
- JSON requests are limited to 16 KiB. Unknown fields, invalid field types, additional JSON values, and oversized bodies are rejected. Decisions are not cacheable grants.
- Public management exposure and management access have canonical event schemas and IoT Shield alerts. OT/SCADA/PLC telemetry shares the configured source and identity policy when it is populated.
- Internet-to-OT, SCADA, PLC, safety, management, and IoT network-flow observations now violate segmentation policy. Zone names are normalized before comparison. Trusted collectors must classify zones correctly.
- The old OT validator's unused source-IP map is removed. A dangerous-command alert now says **Detected**, preserving its existing `ot_command_blocked` alert type for integrations. Detection does not itself reject a packet.

## Configuration

```yaml
management_access:
  allowed_sources: ["10.20.0.0/24"]
  allowed_operators: ["engineer@example.com"]
```

Both lists must be configured together; IP/CIDR syntax and operator names are validated. Wildcard networks are rejected. Empty lists are valid and deny all access-check requests. Start IoT Shield and configure an API write key. Policy changes require an engine restart; reload rejects a changed policy before applying any configuration changes.

## Gateway integration

1. Remove direct public access to the protected equipment. Route management requests through a trusted gateway or protected VPN path, keeping local equipment operation intact.
2. Authenticate the operator independently of the equipment's vulnerable login. Verify session validity and the principal's identity; enforce MFA and resource/action permissions in that upstream access system as appropriate.
3. Build the following JSON from the verified principal, actual client connection, and request being protected. Do not copy verification flags, operator names, or forwarding headers directly from an end user's request. If a reverse proxy is involved, resolve client addresses only through an explicitly trusted proxy configuration.
4. Call the local API or use TLS over a protected network. The write API key belongs only to the trusted integration; giving it to end users lets them submit arbitrary trusted context. No new key-scope or cryptographic identity verifier is added by this change.
5. Forward that request only after HTTP 200 **and** `allowed: true`. Deny on HTTP 403, 400, 401, 429, 503, malformed replies, timeouts, and connection errors. Check every protected request and do not reuse an earlier decision as a session grant.

```json
{
  "source_ip": "10.20.0.7",
  "operator": "engineer@example.com",
  "identity_verified": true,
  "target": "controller-17",
  "action": "configure"
}
```

The response is `{"allowed":true,"reason":"allowed"}` or a deny decision with a reason. The API logs the target, operator, source, and result. Missing/disabled IoT Shield returns HTTP 503. An uninitialized or empty policy returns HTTP 403. Alert-response dry-run does not convert a policy denial into an allow; the gateway decides whether to forward.

`target` and `action` are required audit context, not a per-resource permission model. Listed operators are admitted to the gateway-protected management surface; the gateway/access service must enforce finer permissions. This change does not validate tokens, implement a VPN or reverse proxy, alter controller configuration, or protect a route that bypasses the gateway. A compromised authorized operator or gateway remains a risk.

Send `management_access` telemetry with `source_ip` and the same identity/context fields in `details`, or `management_exposure` with `details.target` and boolean `details.publicly_reachable`. These event paths produce alerts; they are not inline rejection. Configuring the management policy also requires trusted boolean `identity_verified` on monitored OT command events. Existing deployments with no management policy retain their existing OT command inspection.

## Verification

Regression tests cover exact identity matching, IPv4/IPv6/CIDR boundaries, forged identity flags, outside-network access, malformed/oversized requests, API key scope, absent/disabled policy, public exposure, segmentation, registry routing, and atomic restart requirements. The simulated gateway test uses the real authenticated API handler and proves rejected attempts do not touch its backend; an authorized request succeeds, and policy service failure does not forward another request.

This is a controlled gateway demonstration, not a replay of the supermarket attack or a test against Danfoss/Dixell hardware. No refrigeration-specific operating limits or defrost rules were added. The generic OT temperature bounds are unchanged. The Rust shared-config regression checks that the new Go policy section preserves sidecar settings.

The full Go package suite with race detection, CLI build, vet, staticcheck, Gosec, and vulnerability reachability scan pass. Govulncheck reports no affected imported package or reachable function; the existing required-only deprecated OpenPGP advisory remains. Rust formatting, all-feature Clippy, 194 tests with PQC and without packet capture, and cargo audit pass locally. Repository OSV checks pass with the same five optional PQC/paste maintenance exceptions; no new dependency exception was added. Windows packet-capture linking still requires the unavailable `wpcap.lib`; Linux CI covers the all-feature test build.

## Primary evidence

- [CERT-FR refrigeration controller incident, updated October 13](https://www.cert.ssi.gouv.fr/alerte/CERTFR-2026-ALE-012/): confirms controller compromises and recommends removing public management exposure and using protected access.
- [Claroty, October 13](https://claroty.com/team82/research/firmware-to-root-in-30-minutes-how-ai-is-changing-threat-intelligence): states that the precise incident attack path remains unconfirmed.
- [OWASP authorization guidance](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html): deny by default and validate authorization on every request.
