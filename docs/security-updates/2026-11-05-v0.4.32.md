# v0.4.32 — durable off-host auditing and related control-plane fixes

Release date: November 5, 2026 (Asia/Bangkok).

This batch adds durable audit delivery, a dedicated collector, stronger authority checks around delayed requests, and bounded failure handling. It does not provision a collector on your behalf. Install the current main agent on the producer and a separately operated collector host, configure TLS and persistent storage, and verify delivery before relying on the audit boundary. Upgrade an installed Rust sidecar with the agent; its version changes for release alignment, without changing its runtime capabilities.

## Deploy the collector separately

Provision a private, persistent directory owned by the service account, including its parent directories. Use a different host and independently controlled storage/backup credentials from the producer. For example, create a private `collector.yaml`:

```yaml
server:
  host: "0.0.0.0"
  port: 1781
  tls_cert: "/etc/1sec/tls/collector.crt"
  tls_key: "/etc/1sec/tls/collector.key"
audit_receiver:
  enabled: true
  dir: "/var/lib/1sec/audit-collector"
  max_bytes: 134217728
  sources:
    - id: "prod-01"
      token: "REPLACE_WITH_DEDICATED_AUDIT_TOKEN"
```

Generate a separate high-entropy credential for each source, for example `python3 -c 'import secrets; print("1sec_audit_" + secrets.token_urlsafe(32))'`. Securely provision the complete token in the collector configuration and producer secret store. The placeholder above is deliberately invalid; do not deploy it. Tokens require the `1sec_audit_` prefix and at least 43 URL-safe secret characters. Source IDs use 1–128 ASCII letters, digits, `_` or `-`; each source must have a distinct credential.

Run:

```sh
1sec audit-collector --config /etc/1sec/collector.yaml
```

The standalone command requires native TLS, serves `POST /api/v1/audit/ingest` and `GET /health`, and starts no event broker, detector, response executor, embedded dashboard or management API. It does not self-update on startup; update this service deliberately. The optional receiver can also be enabled on a normal engine, whose separate management surface must then be secured. Receiver ingestion requires TLS or a trusted loopback TLS proxy; forwarded headers alone do not establish secure transport.

The ingest credential has no read, delete, reset, policy or operator-management permission. Collector records include a server-generated `received_at`; producers cannot supply that field. Receiver configuration supports up to 32 source journals. The receiver HTTP API has no retention deletion or log-reset operation.

## Enable the producer

Add the following to the engine's private configuration and restart:

```yaml
audit:
  enabled: true
  source_id: "prod-01"
  endpoint: "https://audit.example.com:1781/api/v1/audit/ingest"
  require_remote_ack: true
  max_bytes: 134217728
  # dir: "/var/lib/1sec/audit"
  # ca_file: "/etc/1sec/tls/private-ca.pem"
cloud:
  remote_commands_enabled: false
```

Inject the matching `ONESEC_AUDIT_TOKEN` into the service, or set `audit.auth_token` in its private configuration. The producer's default directory is `bus.data_dir/audit`. The endpoint must be HTTPS, use the exact ingest path, and contain no userinfo, query or fragment. Redirects and ambient HTTP proxies are disabled. Certificate verification remains enabled; `ca_file` provides an explicit private trust root rather than bypassing verification. TLS 1.2 is the minimum supported protocol.

Auditing is disabled until explicitly configured. `require_remote_ack` defaults to true in normal engine configuration: protected HTTP mutations and registered response executors wait for the matching remote intent receipt and its synced local checkpoint before proceeding. A failed, malformed, oversized, late or mismatched receipt prevents admission. Remote delivery for an admission has a five-second budget and serialized, ordered export; filesystem sync latency depends on the underlying storage. A restart record lets the background worker establish delivery before the first management change.

Setting `require_remote_ack: false` deliberately permits locally journaled operations while delivery is pending. It trades protection from producer loss during an outage for availability. Readiness still degrades for a backlog older than 60 seconds; strict mode also degrades when receipt delivery fails or no receipt has been confirmed. Legacy cloud remote commands cannot be enabled with durable auditing: startup, polling and direct dispatch reject that bypass. Cloud telemetry reporting remains separate.

Named operator access remains independently configurable. Enable it for individual human/service attribution; legacy shared keys are explicitly recorded as shared access. Never reuse audit credentials as operator, sensor, broker or shared management keys.

## Evidence and monitoring

The producer journals admitted control-plane mutation intents and handler results, including operator/sensor management, policy changes, approvals, rollback, access decisions and token exchange requests. Event submission and successful read requests are excluded. Automatic and approved executor calls record correlated action intents/results; a wrapper retained in the registered executor map also applies when those executors are used in chains. Unconnected/custom executors and code bypassing that map do not gain an audit guarantee.

Records contain fixed fields: source/stream identity, monotonic sequence, UTC source time, prior/current SHA-256 hash, request/action correlation, trusted actor/credential ID, role at authentication, classified route/method, requested operator role where applicable, resource hash, result status and coarse outcome. Full bodies, headers, query values, provider responses, action details and raw error strings are excluded. Actor IDs can still contain personal information and require appropriate access/retention controls. This is a control-plane audit journal, not a complete event/alert archive or full policy diff.

Inspect `GET /api/v1/audit/status` with a permitted management credential, the embedded dashboard's **Durable audit** tab, and engine `/health`. Monitor `records`, `acknowledged`, `pending`, `oldest_pending_seconds`, `journal_bytes`, `max_bytes`, `max_records`, `last_error`, `denials_pending` and `denials_unjournaled`. The standalone collector's `/health` reports storage readiness. A disk/commit failure prevents future protected operations while reads and liveness remain available.

Denied requests are counted in memory and summarized by the worker rather than writing one record for every unauthenticated attempt. Summaries have their own quarter-journal byte/count budget, including their receipt entries; legitimate traffic does not consume that quota. They also stop near overall capacity to reserve headroom for protected operations. Missing summaries increment an explicit readiness-degrading counter. These counters/summaries are best effort: process loss can discard pending counts, and denied-attempt attribution is not a complete durable per-request trail. Ordinary bounded API logs remain separate.

## Capacity, recovery and limits

Each journal defaults to 128 MiB, configurable from 64 KiB through 1 GiB, and supports at most 100,000 records, including startup and denial-summary records. Synced receipt entries also consume byte capacity. There is no automatic compaction, retention deletion or replication. Monitor headroom and arrange controlled rollover before either limit. At the record-count limit, existing queued records can still drain and committed duplicates can still receive receipts, while new admissions stop. A byte-capacity or storage failure requires operator repair/restart; increasing the byte limit within the supported range may restore headroom.

Preserve both journals, current acknowledgement state, source/stream IDs and collector backups. Stop new operations, drain and verify pending delivery, retain the old journals and their final heads, then provision a fresh source ID/credential for a deliberate new stream. Do not delete pending evidence to clear a capacity alarm. To rotate an ingest credential, preserve source ID and journals, update the collector's private source credential, restart it, then update/restart the producer. Old tokens fail without resetting the retained chain.

Restore the latest verified collector state. Restoring an old producer prefix cannot rewrite the retained collector history; a divergent replay is rejected. A collector restored behind an already acknowledged head cannot accept a later sequence without its missing history. Those conflicts require reconciliation from preserved evidence, not an automatic reset. Customer-specific backup/disaster recovery and large-fleet throughput have not been established by these tests.

An acknowledged intent proves receipt by the configured trusted collector; it does not prove the operation executed. A crash, panic, disconnect or completion-write failure can leave an unresolved intent. Actions already admitted/executing cannot be recalled, and result records may remain locally queued even when intent receipts are mandatory. Diagnose actual host state before retrying an uncertain operation; this release does not add universal action idempotency or a distributed transaction.

File sync and restart tests are not power-cut/storage-hardware certification. Unix initialization syncs journal directories and their parent; Windows uses file `FlushFileBuffers` through Go's `File.Sync` without a portable directory-sync guarantee. Provision parent directories beforehand. Hash chaining is unkeyed integrity/continuity evidence against a retained independent head, not a digital signature, human-presence proof or statutory non-repudiation. A compromised producer can forge future source claims; an administrator controlling both datasets can rewrite both. Independently managed immutable/WORM retention, encryption at rest, external anchoring, SSO/MFA and customer compliance assurance remain separate requirements.

Regression tests use isolated journals, a real TLS receiver and harmless mock executors. They cover commit failure, partial/corrupt state, ownership, concurrent ordered export, lost/false receipts, retries, receiver restart, stale-source backup conflicts, cancellation, denial budgets, credential/transport isolation, secret minimization, delayed revocation, production executor wrapping and the standalone receiver's reduced surface.

Windows portable Rust retains the existing Npcap linking constraint; Linux CI covers full features and real sidecar integration. The existing conditional development-only minimatch finding remains a documented maintenance exception; production dependencies must pass separately. No dependency override, advisory suppression, new container image or Helm package is introduced.
